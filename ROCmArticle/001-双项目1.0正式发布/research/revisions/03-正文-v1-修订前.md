# 给 C# 加上 AMD GPU：HIP + MIGraphX 1.0 正式发布

**从自定义 GPU 计算到 ONNX 模型推理，两个面向 .NET 开发者的开源项目正式发布。**

![C# 与 AMD GPU：HIP 和 MIGraphX 1.0 正式发布](assets/01-cover.png)

## 前言

之前和大家分享过 OpenVINO、TensorRT 的 C# 接口。这段时间，我又把 AMD GPU 这部分继续补了一下：自己写 GPU 计算，用 HIP；已经有 ONNX 模型，用 MIGraphX；应用还是放在熟悉的 C# 工程里。

做过模型部署的朋友应该有体会：模型在官方示例里跑通，只是第一步。真正接进自己的程序，还要处理原生接口、动态库、输入输出、显存和资源释放。如果再加上 GPU 前后处理，Stream 怎么串、异步任务没结束时哪些对象不能释放，也得自己考虑。

我开发这两个项目，就是想让 C# 开发者在使用 AMD GPU 时，有一套可以直接接进工程、遇到问题也能继续定位的接口。

现在，**HIP CSharp API 与 MIGraphX CSharp API 的 1.0 正式版都已经发布。** 配套的 HIP 适配包、Windows 与 Ubuntu 24.04 Runtime 包也已公开，可以通过 NuGet 安装。

先把两个项目地址放在这里，想直接看源码的朋友可以先收藏：


这篇先介绍两个库分别能做什么、这次正式版补齐了哪些内容，以及怎么开始使用。后面也会展示我基于它们继续做的四个应用参考。

> 当前正式组合的主要实际 GPU 验证环境是 Radeon PRO W7900 / `gfx1100`、Windows 和 Ubuntu 24.04 / WSL2，以及 ROCm 10.1 / MIGraphX 2.18。其他 GPU 和运行库组合，需要结合自己的环境验证。

## 一、先说清楚：HIP 和 MIGraphX，各管哪一部分

简单说，**HIP 管自己写的 GPU 计算，MIGraphX 管已有模型的编译和推理。**

| 你的需求 | 可以从哪个项目开始 | 典型工作 |
| --- | --- | --- |
| 我有自己的计算逻辑，想交给 GPU 执行 | HIP CSharp API | 分配显存、复制数据、编译和启动 Kernel |
| 我有 ONNX 模型，想接进 C# 程序 | MIGraphX CSharp API | 解析模型、编译 GPU 程序、设置输入、读取输出 |
| 我想把 GPU 前处理、模型和后处理连起来 | 两个库 + 可选 HIP.Interop | 在 HIP Stream 上提交模型任务，连接设备缓冲区 |

HIP 是 AMD 提供的 GPU 编程接口。HIP CSharp API 在它的 C ABI 之上提供 .NET 绑定，同时封装常用资源对象。应用层可以使用 C# 管理设备、内存和执行过程；自定义 Kernel 仍然使用 HIP C/C++ 编写，再由 HIPRTC（HIP 运行时编译器）编译，或者加载预先编译的模块。

MIGraphX 是 AMD ROCm 生态中的模型推理引擎，负责计算图优化、编译和执行。MIGraphX CSharp API 将这些能力接入 .NET，模型程序、张量、参数和编译选项都有对应的 C# 对象。

两个 Core 可以独立使用。只做模型推理，不需要为了引用 MIGraphX Core 再引入 HIP Core；需要连接 HIP Stream 和显存时，再安装独立的 `HIP.Interop` 适配包。

## 二、HIP CSharp API：让 GPU 计算进入 C# 工程

### 2.1 从设备、显存到 Kernel，有一条连续的调用路径

HIP CSharp API 提供两层入口：常见业务可以先用托管对象，需要贴近原生接口时，再使用生成式低层 API。

| 能力 | 主要对象或入口 | 可以完成什么 |
| --- | --- | --- |
| 运行时与设备 | `HipRuntime`、`HipDevice` | 初始化、设备枚举、版本和设备属性查询 |
| 内存 | `HipDeviceMemory`、`HipPinnedMemory` 等 | 设备内存、锁页主机内存及数据传输 |
| 执行顺序 | `HipStream`、`HipEvent` | 异步提交、同步、事件依赖与计时 |
| 模块与内核 | `HipModule`、`HipKernel` | 加载设备代码、传递参数、启动 Kernel |
| 运行时编译 | `HipRtc`、`HipRtcProgram` | 编译 HIP 源码、查看编译日志、获取设备代码 |
| 高级使用 | Graph、Memory Pool、P2P 等 | 按运行时和设备能力使用对应功能 |

低层绑定包含 **459 个 HIP Runtime 声明和 18 个 HIPRTC 声明**。这能给需要深入原生接口的开发者保留入口；具体函数是否可用，还要看目标 Runtime、硬件能力和对应的实际验证。

### 2.2 接口能调用，资源也要能管清楚

在 C# 里调用 GPU，容易被忽略的是对象生命周期。

比如，把数据异步复制到设备后，主机缓冲区不能马上释放；Kernel 已经排进 Stream，也不能因为当前方法返回，就把它使用的显存清掉。正常路径跑通之后，提交失败、同步失败、清理失败，也都需要有明确的处理方式。

项目围绕这些问题提供显式资源所有权和 `IDisposable` 管理。托管层负责把资源创建、借用和释放的关系表达清楚，异步执行仍遵守 HIP 本身的顺序规则。

这次 1.0 正式版在已有设备、内存和 Kernel 路径上，进一步整理了 Windows HIPRTC 查找、.NET Framework 4.8 和 RID 发布部署，以及互操作与失败回滚等处理。对于准备把库放进实际应用的朋友，这些内容和新增接口一样重要。

## 三、MIGraphX CSharp API：让 ONNX 模型接入 .NET

### 3.1 解析、编译、输入输出，都在 C# 中组织

MIGraphX CSharp API 的主要调用过程很直接：

```text
读取 ONNX → 查询输入形状 → 编译 GPU program → 准备张量 → 执行 → 读取结果
```

模型解析和编译通常放在初始化阶段。同一个 program 后续可以重复使用，持续提交新的输入，避免每处理一张图片就重新解析和编译模型。

项目还提供动态输入尺寸、程序保存/加载、显式模型缓存、类型化张量和加载诊断。需要多输入、多输出时，可以先读取模型的实际信息，再逐项绑定数据。

### 3.2 1.0 正式版补齐了哪些内容

相对于之前的 0.0.2，正式版主要整理了以下几部分：

- **HIP 适配器升级到 HipSharp 1.0.0。** 模型和 HIP 资源使用同一套正式版依赖组合。
- **提供两个平台的独立 Runtime 包。** Windows x64 和 Ubuntu 24.04 x64 可以通过 NuGet 获取 MIGraphX 2.18 引擎及配套插件。
- **补充 MIGraphX 2.18 可选接口。** 包括相关功能组诊断、ONNX 维度参数及执行跟踪元数据等；缺少可选导出时，明确报告对应功能不可用。
- **完善动态形状和缓存路径。** 补充保存、加载、缓存损坏重建及相关资源所有权检查。
- **整理四类完整模型示例。** YOLO26、PaddleOCR、CLIP 和 PP-Structure 纳入当前版本，视觉示例统一使用 OpenCV CSharp API 5.0.0。

这里的 OpenCV 是示例项目使用的图像依赖，MIGraphX Core 与 HIP 适配库本身不因此依赖 OpenCV。

## 四、两个库放在一起，可以怎么用

对于视觉程序，模型前后通常还有不少工作：缩放、归一化、张量排列、结果解码、掩码处理、坐标恢复。需要时，可以把这些计算和模型放进同一个 GPU 流程。

![C# 应用、HIP、MIGraphX 与原生运行时之间的关系](assets/02-api-architecture-v3.png)

*架构示意：两个 Core 各自提供 API，可选 HIP.Interop 负责连接；原生运行库、驱动和硬件分别准备。*

一个常见组合是：

```text
图像上传
   ↓
HIP 缩放、归一化等数值前处理
   ↓
MIGraphX GPU 推理
   ↓
HIP 解码、筛选或掩码计算
   ↓
取回业务需要的结果，交给 C# 应用
```

适配器提供主机/设备输入提交和设备输出接口，并在任务完成之前保留相关资源。`RunDeviceIntoAsync` 可以把输出按同一 Stream 的顺序复制到调用方的设备缓冲区，后面继续接 HIP Kernel。

这样可以减少完整中间张量反复回到 CPU 的需要。具体收益要结合输入规模、传输量和前后处理计算量测量；设备输出仍包含 D2D 复制，使用时也要安排好同步和释放。

历史 Ubuntu HIP Runtime `7.2.1` 仍然可以获取，但属于另一条原生版本路径，不要与新的 MIGraphX 2.18 / ROCm 10.1 组合混装。

## 七、先在自己的项目里跑一次

下面以 Windows x64、.NET 10 为例。先安装兼容的 AMD 驱动；模型推理还需要上面提到的 ROCm 10.1 系统依赖。其他平台的包选择和环境配置见文末部署指南。

### 7.1 HIP：先确认能发现设备

创建控制台项目，安装 Core 和可选 Windows Runtime：

```powershell
dotnet new console -n HipHello -f net10.0
cd HipHello
dotnet add package JYPPX.ROCm.HIP.CSharp.API --version 1.0.0
dotnet add package JYPPX.ROCm.HIP.CSharp.API.Runtime.win-x64 --version 10.1.0
```

将 `Program.cs` 改为下面的代码：

```csharp
using JYPPX.ROCm.HipSharp;

using var runtime = new HipRuntime();
runtime.Initialize();

var versions = runtime.GetVersionInfo();
Console.WriteLine($"HIP Runtime: {versions.RuntimeVersion}");
Console.WriteLine($"HIP Driver:  {versions.DriverVersion}");

foreach (var device in runtime.GetDevices())
{
    Console.WriteLine(device);
}
```

执行 `dotnet run -c Release`。本机使用正式包运行这段代码，输出如下：

```text
HIP Runtime: 7.16.26385
HIP Driver:  7.16.26385
0: AMD Radeon PRO W7900
```

这里的原生 Runtime 报告值与 NuGet 包版本 `10.1.0` 属于不同版本标识。你的输出会随环境变化。能看到真实设备后，可以继续运行仓库里的 HIPRTC VectorAdd，体验编译 Kernel、传参、执行和结果核对。

### 7.2 MIGraphX：先跑一个最小 ONNX

另建一个控制台项目，安装模型接口和 Windows 引擎包：

```powershell
dotnet new console -n MigraphxHello -f net10.0
cd MigraphxHello
dotnet add package JYPPX.ROCm.MIGraphX.CSharp.API --version 1.0.0
dotnet add package JYPPX.ROCm.MIGraphX.CSharp.API.Runtime.win-x64 --version 1.0.0
```

仓库提供一个可生成的 Identity 测试模型，输入名为 `input`，类型为 `float32[1,4]`，输出与输入一致。安装 Git 和 PowerShell 7 后，在当前项目目录执行：

```powershell
git clone --depth 1 --branch v1.0.0 https://github.com/guojin-yan/MIGraphX-CSharp-API.git ../MIGraphX-CSharp-API-v1.0.0
pwsh -File ../MIGraphX-CSharp-API-v1.0.0/tests/fixtures/generate-onnx-identity.ps1 -OutputPath "$PWD/identity.onnx"
```

这个模型用于看清调用过程。本例先由 .NET 读取文件，再从内存解析 ONNX。换成业务模型时，需要按实际输入名、尺寸、类型和预处理规则准备数据。

```csharp
using JYPPX.ROCm.MIGraphXSharp;

var environment = MIGraphXEnvironment.ProbeSystem();
if (!environment.ObjectsExecuted)
    throw new InvalidOperationException(string.Join("; ",
        environment.Diagnostics.Select(d => d.Message)));
string native = environment.LoadedPath!;

using var options = new MIGraphXOnnxOptions(native);
using var program = MIGraphXProgram.ParseOnnxBuffer(
    File.ReadAllBytes("identity.onnx"), options);
using var target = new MIGraphXTarget(native, "gpu");
using var compileOptions = new MIGraphXCompileOptions(native, offloadCopy: true);
program.Compile(target, compileOptions);

var shape = program.GetParameterShapes()["input"];
using var input = MIGraphXArgument.Create(native, shape, new[] { 1f, 2f, 3f, 4f });
using var parameters = new MIGraphXParameterMap(native);
parameters.Add("input", input);

using var outputs = program.Run(parameters);
Console.WriteLine(string.Join(", ", outputs[0].ToArray<float>()));
```

保存为 `Program.cs`，执行 `dotnet run -c Release`，该模型的预期输出是：

```text
1, 2, 3, 4
```

这里先用 `offloadCopy: true`，由原生引擎安排主机输入输出的传输，便于理解模型调用。后续需要自己管理显存和 Stream 时，再切换到对应的 HIP 互操作路径。

对于持续处理数据的程序，把解析、编译和资源初始化放在启动阶段，后续复用 program；`using` 则负责在退出作用域时释放相应对象。

## 八、再往前一步：我用它们做了四个应用参考

库写完以后，我还想继续看看：当输入导入、任务处理、人工复核和报告导出都加上之后，这些接口在完整应用里应该怎么组织。

所以，我又基于公开的 HIP / MIGraphX 包，继续做了一个 ROCm C# 应用集合。目前有下面四个方向，各项目根据实际需求选用对应库。**这些是正在开发、可以运行的应用参考，领域精度与生产验收仍在继续完善。**

### 8.1 SurfaceLab：工业表面质检与复核工作台

![SurfaceLab：图像批次、GPU 检测、人工复核与证据导出](assets/03-surfacelab-v3.png)

*应用流程示意：批次图像经 HIP 规则或 MIGraphX 模型检测，再人工复核并导出证据；机器人为视觉引导角色。*

SurfaceLab 把图像批次、配方、检测、复核和证据报告放进一个本机工作台。可以使用 CPU 参考规则、真实 HIP GPU 规则，也可以准备实验性 MIGraphX 异常模型，查看原图、掩码、区域和热图。

我比较看重的是结果后面的流程：机器结果保留，人工意见单独记录，修改有原因和历史，最后导出图片、JSON、CSV 和离线报告。当前模型还没有达到独立工业验收目标，仍保留人工复核。

### 8.2 SignalDiagnostics：从波形到频谱，把分析结果留得下来

![SignalDiagnostics：离线信号、HIP FFT、频谱分析、规则复核与归档](assets/04-signal-diagnostics-v3.png)

*离线流程示意：CSV 信号 → HIP 分窗 FFT → 频谱 / PSD → 返回原始区间复核 → 报告归档。*

这个项目使用 HIP 实现 FFT，处理单通道离线信号，生成频谱、功率谱密度（PSD）、分窗规则结果和可独立打开的报告。分析结果能够回到原始样本区间，方便继续检查。

它主要展示 HIP 自定义计算的使用方式，不依赖 MIGraphX。当前的规则命中表示“需要复核”，还不能据此给出成熟的故障分类、剩余寿命或设备安全结论。

### 8.3 DocumentEvidence：OCR 之后，还有字段核验与人工纠正

![DocumentEvidence：指定行区域 OCR、字段与金额核验、人工修改和证据导出](assets/05-document-evidence-v3.png)

*流程示意：明确指定的文字行 → MIGraphX OCR → 字段与金额核验 → 人工修改和证据导出，机器值与修改分别保留。*

DocumentEvidence 可以导入已有 OCR 证据，也能通过 MIGraphX 识别页面里明确指定的行区域，再按模板提取字段，检查金额和置信度，保留人工纠正与批准记录，导出 HTML、JSON 和 CSV。

这里会分别保留机器读取值和人工最终值，便于回看问题出在哪里。自动整页检测是另一个开发入口，目前 GPU 数值检查仍有失败，完整票据识别质量也需要继续验证。

### 8.4 VideoEventSearch：把视频里的候选事件，连接回原始帧

![VideoEventSearch：离线街景视频、检测跟踪、规则事件、候选索引与原帧回看](assets/06-video-event-search-v3.png)

*离线流程示意：视频原始帧 / PTS → MIGraphX 检测与跟踪 → 区域、越线、停留规则 → 候选事件索引与原帧回看；画面不代表实际检测结果。*

VideoEventSearch 从离线视频的原始时间戳（PTS）和图像帧出发，结合 MIGraphX 检测、跟踪与区域/越线等规则，建立候选事件索引，并保留对应的原帧证据。

真实媒体和 GPU 推理已有运行记录，后面还需要独立人工标注来评估事件质量。这个项目目前展示的是离线处理和证据组织过程，后续会再展开模型、时间语义与事件评估。

这四个应用后面会按开发进度分别介绍，源码入口也会在相应专题中整理。对这篇发布文来说，更希望让大家看到：两个库既能用于小型计算示例，也能继续接进有输入、任务、复核和输出的 C# 应用。

## 九、当前验证到了哪里

目标框架覆盖说明能构建和打包到哪些 .NET 目标；实际运行仍要看操作系统、原生库、驱动和 GPU。正式版相关的主要实测记录如下：
