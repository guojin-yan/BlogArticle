## 一、这篇文章要让读者记住什么

**我把 AMD GPU 的自定义计算和模型推理两部分，整理成了可以在 C# 中使用的两个正式版开源项目：HIP CSharp API 与 MIGraphX CSharp API。需要时，二者还能通过独立适配包组合使用。**

面向已有 C#/.NET 工程、想接入 AMD GPU 的开发者，尤其是工业视觉、OCR、信号处理、桌面和服务程序开发者。阅读结束后，读者应知道两个库各负责什么、1.0 带来哪些实际变化、怎样开始运行，以及在哪里获取源码和反馈问题。

文章主类型：正式版本发布；次类型：项目介绍。以“项目正式可获取、可以怎样使用”为主线，用应用展示增强吸引力。

### 一、两个项目分别解决什么问题（约 450 字）

用对照表建立认知，首次出现时简单解释 HIP、MIGraphX 和 HIPRTC。

| 项目 | 读者的需求 | 主要调用对象 |
| --- | --- | --- |
| HIP CSharp API | 自定义 GPU 计算、设备内存、异步执行和 Kernel | `HipRuntime`、`HipStream`、`HipModule`、`HipKernel`、`HipRtc` |
| MIGraphX CSharp API | 解析 ONNX、编译模型、绑定输入并读取结果 | `MIGraphXProgram`、`MIGraphXArgument`、`MIGraphXParameterMap` |
| 可选 HIP.Interop | 将模型放进已有 HIP Stream 与设备缓冲区流程 | `MIGraphXHipExecution` 等 |

说明两个 Core 可以独立使用，适配包才依赖二者。库内模型示例与后面的应用集合是两组素材，不混称同一组“案例”。

### 二、1.0 正式版，这次值得关注什么（约 700 字）

用一张 5–6 行更新表概括，再挑最重要的变化说明。

HIP 部分：

- 托管资源所有者和低层 C ABI 两条入口，覆盖设备、内存、Stream/Event、Module/Kernel 和 HIPRTC。
- 15 个目标框架的统一接口面；构建兼容与实际运行验证分别说明。
- Windows HIPRTC 发现及 net48 / RID 部署修复，异步资源与失败回滚处理。
- Core 1.0.0 与 Windows / Ubuntu HIP Runtime 10.1.0 的公开获取路径。

MIGraphX 部分：

- HIP 适配器升级到 HipSharp 1.0.0；MIGraphX 2.18 的可选接口与诊断。
- 动态形状、程序保存/加载及缓存行为修复；缓存恢复按当前指南使用，避免承诺跨设备、跨版本通用。
- 独立 Windows / Ubuntu MIGraphX Runtime 1.0.0，内部引擎版本为 2.18。
- YOLO26、PaddleOCR、CLIP、PP-Structure 四类库内示例；视觉依赖迁移到 OpenCV。OpenCV 属于示例依赖，Core 不因此依赖图像库。

对比基线是已经公开的 HIP 0.10.0 和 MIGraphX 0.0.2。已有能力写“正式版保留/整理”，不要把全部内容都写成 1.0 新增。

### 三、从 C# 调用到 GPU，两个库怎样配合（约 450 字）

放架构图。明确托管 API、原生用户态库与驱动/硬件的层次。

用一个实际图像处理过程说明组合用途：输入 → HIP 数值前处理 → MIGraphX GPU 推理 → HIP 后处理 → 取回必要结果。注明这是可选组合方式；实际各示例的处理位置以其代码为准。

用一句话解释适配器的价值：提交后资源租约保留到 Stream 完成，再按顺序释放。提到 `RunDeviceIntoAsync` 使用同一 Stream 上的 D2D 输出复制，不能写成“零拷贝”，也不能把每个应用都说成全程 GPU。

### 四、在自己的项目中先用起来（约 800 字）

首先放精简环境表：当前正式组合的实际 GPU 验证以 W7900/gfx1100、Windows 与 Ubuntu 24.04/WSL2、ROCm 10.1/MIGraphX 2.18 为基线。15 TFM 表示托管包构建范围；首次示例优先现代 .NET，源码示例使用 .NET 10。

按两条路径组织，避免把七个包全部塞给读者：

1. **只做 HIP 计算：** Core 1.0.0 + 当前平台的可选 HIP Runtime 10.1.0，先运行设备枚举，再指向 HIPRTC VectorAdd。
2. **做模型推理：** MIGraphX Core 1.0.0 + 对应 MIGraphX Runtime 1.0.0 + 匹配的 ROCm 10.1 系统依赖；需要 HIP 流集成再加 HIP.Interop 1.0.0。

正文只完整展开一个平台的命令，另一个平台用对应包名和指南承接。推荐 Windows 为主路径，符合桌面 C# 读者的使用习惯；Ubuntu 入口并列保留。

代码安排：

- HIP 约 15 行，使用源码 `EnvironmentAndDevice` 的真实调用，输出版本和设备。
- MIGraphX 约 25–35 行，使用 `ProbeSystem()` 发现库，解析一个输入/输出合同已知的小 ONNX，编译一次后运行，`using` 明确释放。
- MIGraphX 的最小模型必须随本文提供或引用可公开下载的固定测试模型；没有模型和真实输出前，不把该段标成“复制即可运行”。

本次是资料规划，没有新跑 GPU 代码或新做性能测量。正文阶段应使用独立文章示例目录验证命令与输出，验证产物留在本篇目录内。

### 五、不止是 API：我用它们做了四个应用参考（约 600 字）

引导句：为了看看这些接口放进完整应用后怎么使用，我又继续做了一个 ROCm C# 项目集合。当前有四个可运行方向，仍在开发和验证中。

每个项目一张图，图后一个短段落，统一写“输入 → 处理 → 可见输出”，不深入训练和算法评估。

| 项目 | 展示重点 | 调用关系与本篇边界 |
| --- | --- | --- |
| SurfaceLab | 批次导入、缺陷叠加/热图、人工复核、报告 | HIP 规则与实验 MIGraphX 模型均有实际路径；质量目标尚未达成，默认保留人工复核 |
| SignalDiagnostics | 波形、频谱/PSD、分窗规则、来源和报告 | 使用 HIP FFT；不依赖 MIGraphX，不宣传成成熟故障分类器 |
| DocumentEvidence | 明确行区域 OCR、字段核验、纠正历史和导出 | 使用 MIGraphX OCR；自动页检测是另一个显式开发入口，其 GPU 数值验证失败，不包装成自动票据识别成功案例 |
| VideoEventSearch | 原始 PTS、检测/跟踪、事件索引和原帧证据 | 使用 MIGraphX 检测；真实视频尚无独立人工事件标注，不能给事件准确率或暗示 0 事件代表可靠 |
